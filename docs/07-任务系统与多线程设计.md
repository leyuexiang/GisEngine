# 07 任务系统与多线程设计

## 1. 设计目标

借鉴参考工程生产者-消费者任务系统，但适配浏览器 Worker 和结构化克隆限制，形成可取消、可观测、可限流的任务调度器。

## 2. 任务分类

| 类型 | 执行位置 | 示例 |
|---|---|---|
| IO 任务 | Worker/浏览器网络 | fetch、读取缓存 |
| 解码任务 | Worker | glTF、KTX2、矢量、地形 |
| CPU 计算 | Worker | 网格生成、碰撞预处理 |
| 主线程任务 | 主线程 | ECS、场景、编辑器 |
| GPU 任务 | 主线程编码/队列 | Buffer/Texture 上传、提交 |

## 3. 任务契约

```ts
interface EngineTask<T> {
  id: number;
  kind: string;
  priority: number;
  signal: AbortSignal;
  run(context: TaskContext): Promise<T>;
}
```

任务结果必须携带版本或目标句柄，接收方在应用前校验版本，避免节点已销毁时写入旧数据。

## 4. Worker 池

Worker 数量默认不超过 `min(硬件并发数 - 1, 4)`，并可由配置覆盖。调度采用优先队列；长任务需要分片或让出执行权，防止单个解码任务阻塞所有瓦片。

## 5. 取消、超时和重试

请求取消通过 AbortSignal 向下传播；Worker 任务在安全检查点响应取消。网络错误采用指数退避，数据格式错误不自动重试。超时与取消都要释放 Transferable 缓冲区。

## 6. GPU 上传队列

UploadQueue 聚合每帧待上传资源，按字节预算执行。资源上传完成后发布 `AssetResident` 或 `TileResident` 事件；渲染器只消费已驻留句柄。

## 7. 可观测性

每个任务记录排队时长、执行时长、等待原因、输入字节、输出字节、取消原因和失败堆栈。调试面板显示队列深度、Worker 利用率和上传积压。

## 8. 验收标准

- 任务可按优先级调度且不饿死低优先级任务。
- 取消任务不会产生未处理 Promise rejection。
- Worker 与主线程传输不发生不必要的数据复制。
- GPU 上传有上限，不能在单帧造成长任务。
